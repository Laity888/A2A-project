# 长期记忆与用户偏好：结构化存储 + 答复侧注入，刻意不做向量语义记忆

Status: accepted

长期记忆 / 用户偏好这一簇术语的边界见 `GLOSSARY.md`。

## 决策

长期记忆与用户偏好采用**结构化 MySQL 存储**（`user_profiles` 偏好 KV + `query_history` 意图/问题流水），由**接待按 `user_id` 无状态读取、经 A2A 传给答复 Agent 注入其 system 提示词**；**刻意不引入向量/语义记忆**（那是被明确推迟的独立一期）。选它是因为：贴合本项目"多 Agent 分离、`user_id` 每请求才知"的形态，成本可控，且与已有的语义缓存职责清晰分离。

## 考虑过但否决的方案

- **向量语义记忆（复用 Milvus 做"按含义回忆过去事实"）**：能力更强，但工作量大、且会把"记忆"和"语义缓存"两套向量用途搅在一起。→ 推迟到二期，届时单开集合（如 `cs_mem_lzs`），与本期不冲突。
- **参考方案里的"每用户常驻实例 + 内存镜像 + 启动加载"**：那是单体主 Agent 的形态。本项目是按请求拿 `user_id`、接待单 worker，故改为**无状态、按 `user_id` 传参、每请求直查**（读一次 profile/history 是走索引的小查询，成本可忽略）。这是有意偏离，勿被"优化"回常驻实例。
- **连接池（共享 MySQLManager）**：本地单 worker 收益极小，且需新增依赖。→ 暂不做，沿用既有 `connection_factory` 每操作连接。
- **自动从对话抽取偏好（LLM 检测"我以后都…"）**：易误记。→ 一期只做**显式 UI/API 设置**，自动抽取与偏好注入 triage/ReAct 一并推迟。

## 影响

- 记忆读写用 `asyncio.to_thread` 卸载阻塞、并**内联 `await`**（非 fire-and-forget），以保证记录落库 + 测试确定性；代价是缓存命中路径多等一次本地写入（毫秒级）。
- **缓存按"偏好签名"作用域**：L1 key 与 L2（Milvus）都折入 `pref_sig = hash(排序后的偏好)`，改任一偏好即签名变 → 缓存 miss → 按新偏好重生成。因此"命中缓存返回旧风格答案"的问题已修；缓存命中仍是安全的（存的答案本就在同一 `pref_sig` 下生成），且保留"跳过检索/生成"的省算力收益。代价：偏好读要提前到 L1 之前（每请求多一次走索引的小查询）、缓存按风格分片。
- 偏好只影响**最终答复措辞**，不影响分流与工具选择；`query_history` 目前是朴素追加流水，尚无去重/合并/冲突覆盖/衰减遗忘——这些随二期语义记忆一起做。
- 与语义缓存分表分集合，`user_profiles`/`query_history` 专记"关于用户"，语义缓存集合专记"问题→答案"（加 `pref_sig` 字段后集合改名为 `cs_qc2_lzs`，旧 `cs_qc_lzs` 可直接删）。命名与用途不得混用。
