### 推回（技术理由）

**Standards 轴 (b) · Data Clumps** — `(text, user_id, pref_sig)` 抽 `CacheKey` 类型：**推回**。
理由：`AnswerCache.get/set` 与 `SemanticCache.lookup/record` 公共 API 均是 `(text, user_id, pref_sig)` 位置参数 + `pref_sig` 关键字；抽 `CacheKey` 要么扩 API 双写兼容层（+2 方法、现有单测不动但 Speculative Generality 反过来命中），要么改现有 API 签名（13+ 单测要跟着改）。当前 service.py 内 `(text, user_id, pref_sig)` 只 4 处出现且字段稳定为三，留待真出现第 4 个键分量时再抽。若后续加 `context_id` 作第五分量或做分布式缓存 keying，届时重开。

**Standards 轴 judgement · Primitive Obsession (`trace["intent"]="cache"`)** — **推回，已在 ADR-0003 明确定性**。
理由：`"cache"` 是文档级合成标记（区分 L1 命中 vs L2 语义缓存命中 vs 主链路），triage 枚举本身在 `agents/reception/triage.py:INTENTS` 仍四值干净。给合成 intent 建独立类型是过度形式化；ADR-0003 里已显式描述该"intent 字段跨合成值与枚举并存"的边界。

**Spec 轴 (a)1 · `parent_task_id` 从未落地** — **推回**（改为落地 ADR 记录不做）。
理由：见 ADR-0004。落地即死代码，作品集 UI/日志无按 Task 反查入口，实测端到端只靠 `context_id` 归组。
